TALENTBRIDGEAI - GOOGLE AUTHENTICATION AND ADMIN REVIEW
========================================================

Report date: 2026-11-12
Project: TalentBridgeAI
Scope: Existing Django authentication, Google OAuth readiness, admin account
       state, focused tests, and requested deliverables.

EXECUTIVE SUMMARY
-----------------
The project already contains a server-side Google OpenID Connect flow built
with django-allauth. The actual blocker is configuration: the private project
root .env has neither GOOGLE_OAUTH_CLIENT_ID nor
GOOGLE_OAUTH_CLIENT_SECRET configured. Django therefore correctly disables
the Google buttons and does not start an OAuth request. No credentials were
read into this report or printed during the audit.

The active database is database/TalentBridgeAI.sqlite3. It contains zero
auth_user rows and therefore zero staff or superuser accounts. No password
reset, account creation, database restore, or destructive operation was
performed. A test-database superuser can authenticate and open Django Admin.

REAL GOOGLE SIGN-IN IS NOT YET END-TO-END TESTED. A valid Google Cloud Web
OAuth client, an allowed Google test account, and the user's interactive
approval are required. The Google button remains explicitly unavailable
until the credentials are configured locally.

The project uses Django 5.2.19, django-allauth 65.22.0, Python 3.12.10, and

The live login page is rendered from the repository-root pages/login.html by
the Django route /login/. The allauth URL include is mounted at /accounts/.
The custom OAuth start endpoint is /auth/social/google/.

2. ORIGINAL PROBLEM AND ROOT CAUSE
----------------------------------
The reported notice was:
"Google sign-in is unavailable until this site is connected to a Google OAuth
app."

Inspection of the private .env checked only whether values were present; no
secret values were read or displayed. Both Google OAuth variables are
unconfigured. There are also zero Google SocialApp rows in the active database.
The settings add the Google provider only when both values are present, and
google_oauth_configured() reports false otherwise. The login and signup
templates consequently disable the button and show a configuration notice.
This is the safe behavior, not a successful Google login.

The OAuth routes, Google provider, callback handling, signup adapter, and
security-related tests already existed. The root cause was not a missing or
duplicate authentication system; it was the absence of the required Google
Cloud OAuth client credentials. The consent-screen configuration cannot be
verified until a valid Google Cloud client is supplied.

5. GOOGLE OAUTH IMPLEMENTATION AND SECURITY
-------------------------------------------
The existing django-allauth Google provider is retained. The login and both
signup pages submit to the real, CSRF-protected POST endpoint
/auth/social/google/. Allauth creates and validates OAuth state and handles
the authorization-code exchange and callback. The callback was resolved from
the running URL configuration:

  http://127.0.0.1:8000/accounts/google/login/callback/

The Google provider uses allauth's ID-token verifier. It checks issuer,
audience, and expiration, obtains Google's signing keys when signature
verification is required, and applies the library's JWT replay check when a
token includes a jti claim. Allauth's Google provider marks email addresses
verified only from Google's verified-email claim. Automatic email-based
account authentication/connection is enabled only for the Google provider.
Tests confirm an unverified email does not authenticate an existing account.

SOCIALACCOUNT_AUTO_SIGNUP is false. A first-time Google user completes the
existing account form, including account role; employer signup requires a
company name and remains pending approval. The requested role is kept in the
server session, not trusted from a modified form. Redirect destinations are
restricted to safe local URLs. Existing Django session login is used, and
logout is POST-only.

The new google-oauth.js loading state disables a submitted Google button and
announces that it is connecting. When credentials are absent, all three
Google buttons remain disabled. The login heading no longer implies Google
sign-in is ready in that state. Email/password authentication remains
available.

The static-preview demo handler is separate from the Django server and only
runs in its explicit static-preview mode; it is not the live Django
authentication flow.

6. ENVIRONMENT AND GOOGLE CLOUD CONFIGURATION
---------------------------------------------
Required private environment values:

  GOOGLE_OAUTH_CLIENT_ID=<Web application client ID>
  GOOGLE_OAUTH_CLIENT_SECRET=<Web application client secret>

Neither value is hardcoded in source or included in this report. Use
CONNECT_GOOGLE_OAUTH.bat from the project root. It accepts the Client Secret
through hidden input and stores the values in the private root .env. Do not
paste credentials into chat or commit/share .env.

Google Cloud Console setup:
1. Create/select a Google Cloud project and configure the OAuth consent screen.
2. Choose Internal or External audience as appropriate; add test users while
   the external app is in Testing.
3. Create a Web application OAuth client using the openid, email, and profile
   scopes.
4. Add this local authorized JavaScript origin:
   http://127.0.0.1:8000
5. Add this exact redirect URI:
   http://127.0.0.1:8000/accounts/google/login/callback/
6. Configure separate exact HTTPS origin and callback values for production.

After local credentials are saved, restart Django and use
http://127.0.0.1:8000/login/. Do not use the static Go Live preview for OAuth.
The detailed setup is documented in docs/setup/GOOGLE_OAUTH_SETUP.md.

database, create an authorized administrator only after confirming the desired
account details, using Django's interactive createsuperuser command.
